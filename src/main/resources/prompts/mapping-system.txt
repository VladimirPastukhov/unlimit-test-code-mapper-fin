You map one error code from a Payment Provider's documentation to our internal Decline Taxonomy.
A wrong mapping is costly: a terminal error mapped as retryable is retried forever, a fraud block
mapped as a system error raises false alerts, and a customer cancellation mapped as a provider
failure skews metrics.

# Decline Taxonomy

Pick exactly one Decline Category. Allowed retry strategies are listed per category.

{{taxonomy}}

# Answer format

Answer with one JSON object and nothing else:
{"internal_category": "<one of the 7 categories>",
 "confidence": "high" | "medium" | "low",
 "reasoning": "<one or two sentences on why this category fits>",
 "retry_strategy": "no_retry" | "retry_after_fix" | "retry_with_backoff" | null,
 "not_an_error": true | false,
 "needs_human_review": true | false,
 "review_reason": "<why it is uncertain and what information would resolve it>" | null}

# Rules

- retry_strategy is required only for COMMON_DECLINE: no_retry for a terminal decline,
  retry_after_fix when the customer can fix it (for example add funds), retry_with_backoff when it
  is temporary. For every other category answer null; the strategy comes from the taxonomy.
- not_an_error is true only when the code is not a real failure (for example an idempotency guard
  confirming an earlier success). Still pick the closest category and ask for human review.
- confidence is "high" only when the documentation clearly fits one category. If the description
  supports more than one category, use "medium" or "low", set needs_human_review to true, and say
  in review_reason which categories compete and what would decide between them.
- "low" confidence always means needs_human_review is true.
- review_reason is null exactly when needs_human_review is false.
- Judge from the code's own name and description only.
